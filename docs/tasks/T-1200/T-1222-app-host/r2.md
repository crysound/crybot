   - 跳转参数原样透传：从 `req.url` 的 `?` 之后截取，不要经 WHATWG URL 重组。
2. **主域名带有效 JWT 被误判成 App 通道（`server/cf-access.ts:39-43`）。** `cfAccess` 有三处提前 `return null`（有效 `cry_sess_` Bearer、事件 ticket、没有 accessIdentity 的 cookie 会话），没走 `jwtVerify` 就没打标记，结果主域名上用配对码或邮箱登录过的浏览器访问 `/auth/app-handoff` 被 404。改法：只要请求带了 `Cf-Access-Jwt-Assertion`，先验签并打标记，再走原来的短路（判断逻辑不变，只是标记提前）。补端到端用例：主域名 + 有效 JWT（测试签发）+ cookie 会话 → `/auth/app-handoff` 不是 404。
3. **`server/app-host.e2e.test.ts` 要真的端到端。** 照 main 上 `server/app-links.e2e.test.ts` 的做法（`verificationServerArgs` + `freePortBlock` 起真实服务），按规格 3.5 的清单逐条请求、逐条断言状态码，两组 Host（App 通道；另一主机名 + `X-Forwarded-For`）都跑；加 WebSocket upgrade 用例；`/auth/app-handoff` 的「有效 JWT」用测试签发的 JWT；`/desktop-updates/` 真的取文件；「什么都没配时行为不变」用真实请求回归。沙箱不能监听端口，照实写，协调者在沙箱外跑。
4. **安卓不改。** 原生登录页归任务 05，`crybot://feishu` 和 feishu App Link 入口都留给任务 05。本任务 `mobile/android/**` 保持 main 原样。
5. **兜底页测试要测行为。** 直接请求 `/auth/app-return` 和 `/auth/feishu/app-return` 页面，参数传 `//evil.example.com`、`https://evil.example.com`、`javascript:`、引号、`<script>`，断言 `href` 和 `location.replace` 的目标都以 `crybot://auth?` / `crybot://feishu?` 开头、正文没有未转义的 `<script>`（只允许页面自己那一个）、响应头（`Cache-Control: no-store`、`Referrer-Policy: no-referrer`、CSP）齐全；没配飞书时 `/auth/feishu/app-return` 404。
