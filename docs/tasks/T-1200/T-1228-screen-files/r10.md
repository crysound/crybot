## 必改：抢救的打包和解包没有字节上限
- 位置：`server/screen-profile-files.ts` 的 `packageScreenProfile`（`pipeline(output, createWriteStream(archive))`）和 `extractScreenProfile`。`PROFILE_BYTES_MAX` 目前只在 `transferProfile` 检查，那时归档已经落盘、也已经解包过一次。
- 攻击路径：屏里的程序在 `~/.config/chromium` 等目录造一个超大稀疏文件（如 `truncate -s 10T`）。容器内 `tar -cf -` 按表观大小展开输出，宿主把它整个写进临时目录的归档，直到 5 分钟超时才停；解包到暂存目录时再写一份。宿主磁盘会被写满。
- 改法：
  1. 打包：在 stdout 和写文件之间加计数 Transform，累计字节超过上限（`PROFILE_BYTES_MAX` 加一点 tar 头开销，取值写清理由）就报错并 SIGKILL 子进程，删掉半截归档，抢救按失败处理（保留现有 rescue-pending 语义和错误文案风格）。
  2. 解包：在 filter 里对 File 条目累加 `entry.size`，超过 `PROFILE_BYTES_MAX` 就 reject；解包前也用归档实际大小确认一次。
  3. 确保暂存目录里出现 mode 000 的目录时清理仍然成功（可以用 tar 的 `noChmod`，或者清理前先放开权限；选哪种在报告里说明，并确认登录相关文件的权限不受影响）。
  4. 上限要能在测试里注入一个小值（例如参数或内部选项），不要为测试真写 1 GiB。
- 补测试：
  - 假 runtime 的 stdout 无限输出数据：抢救 reject，归档文件不超过上限，子进程被杀，没有残留归档。
  - 归档里文件总大小超过上限：解包 reject。
- 解包过滤的其他规则一律不动。
