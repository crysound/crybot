## 必改（安全审查中危）：解包过滤器补盘符路径和大小写/Unicode 不敏感文件系统
- 位置：`server/screen-profile-files.ts:94-122`，即 `extractScreenProfile` 的 filter。
- 问题一：没有拒绝 `C:/x`、`C:x` 这类盘符路径，也没有拒绝路径段里的 `:`。Windows 宿主上，`path.resolve` 会把它们变成盘符绝对路径，可以写到解包目录之外。
- 问题二：软链接前缀用字面方式比较。在大小写不敏感的文件系统（macOS、Windows）上，先放软链接 `x`，再放 `X/payload`，就能绕过前缀检查。Unicode 规范化写法不同时也是同样的问题。
- 改法：
  - 每个路径段都必须匹配 `^[^\\/:\0]+$`，并拒绝匹配 `^[A-Za-z]:` 的路径。软链接目标里出现 `:` 也拒绝。
  - links 的存储和前缀比较统一使用 `normalized.normalize("NFC").toLowerCase()` 作为比较键，实际写盘的路径不变。条目经大小写折叠后与已有软链接相同或落在它下面时，一律拒绝。
- 补测试：`C:/x`、`C:x`、`a/b:c`，以及「软链接 `x` 之后跟 `X/f`」和「NFD 写法的软链接名之后跟 NFC 写法的子路径」两种情况，都要 reject，保留 rescue-pending，外部目录没有新文件。

## 一并修：文件型密钥先核对屏归属再入库
- 位置：`server/host/secret-cards.ts:282-284`（`storeCustomSecretWithAccess`）、手机路径 `:590` 附近、同步入口 `storeCustomSecret` `:245-248`。
- 问题：现在先执行 `vaultStore.saveSecret`，再在 `handOverWithAccess` 里核对屏归属。屏已经改分给别人时，用户看到「保存失败」，但值已经存进了 Vault；下次同名请求还会直接复用这个值，不再弹卡片。
- 改法：`saveSecret` 之前先调用 `accessFor(secret.vm, botId, threadId)` 做预检，拿不到访问器就抛出与现在相同的 409 错误。改分用例里补一条断言：Vault 里没有这条密钥。
