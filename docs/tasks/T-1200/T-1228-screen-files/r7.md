# T-1228-screen-files 第 7 轮（复审 + 安全审查返工）

前几轮说明在 `docs/tasks/T-1200/T-1228-screen-files/` 下；第 6 轮改动在 worktree（未提交），在此基础上改。复审员实测：r6 点名的情况（`..`、绝对路径、经软链接写入、硬链接、反斜杠、设备文件和 FIFO）都已拦住，错误走 Promise。本轮只改下面三处。

## 必改 1：带末尾斜杠的软链接能绕过前缀拦截
- 位置：`server/screen-profile-files.ts:97,103,118`。
- 现状：`posix.normalize("./x/")` 的结果是 `"x/"`，带着末尾斜杠存进了 links。随后的条目 `x/ESC` 既不等于 `"x/"`，也不以 `"x//"` 开头，所以前缀匹配不上。node-tar 建软链接时会去掉末尾斜杠，实际建出的是 `x`；加上 `preservePaths: true`，建父目录时会跟着软链接走，文件就写到了外部目录。抢救最后还返回 "rescued"。`./x//` 也会规范化成 `x/`，是同一个问题。
- 改法：规范化后去掉末尾斜杠，例如 `posix.normalize(p).replace(/\/+$/, "")`。结果为空或为 `.` 时，只允许该条目是 Directory。存 links 和做前缀比对都用这个结果。另外，原始路径以 `/` 结尾的 SymbolicLink 条目直接拒绝。
- 补测试：hostile 用例加 `./x/` 和 `./x//` 两种，断言外部目录没有新文件、rescue 被 reject。

## 必改 2：根内的相对 `../` 软链接目标不能拒
- 位置：`server/screen-profile-files.ts:115`。
- 现状：软链接目标只要含一段 `..` 就被拒绝。`.local/bin/app -> ../share/app/run` 这类正常链接（npm 全局 bin、flatpak 用户导出都是这种）会让抢救一直 reject，旧容器就永远无法重建。这也违背了 r2 第 4 条「软链接原样保留」。
- 改法：只拒绝三种软链接目标：含 `\` 的、空的、按 `posix.normalize(posix.join(posix.dirname(条目), 目标))` 算出来越出根的相对目标。根内的 `../` 放行，绝对目标照旧放行。宿主不会跟随软链接：链接下面的条目由前缀规则拒绝，transferProfile 只做 lstat 和 readlink。
- 补测试：`.local/bin/app -> ../share/app/run` 能抢救成功，链接原文保留；`a/l -> ../../x` 这种越根目标被拒绝。

## 必改 3（安全审查中危）：文件型密钥卡片投递前要核对屏归属
- 位置：`server/host/secret-cards.ts:61` 的 `fileAccess?(vm: string)`，`:261-268` 的 `accessFor` 和 `handOverWithAccess`，`:~724` 的 `mintFileWithAccess`；`server/secret-vault.ts` 的 `writeWithAccess`。
- 攻击路径：机器人 A 在屏 s2 上发出文件卡片，卡片记下 `shared:s2`。之后 s2 被重新分给机器人 B，用户再在 A 的卡片里填密钥。这时密钥会以 `crybot-s2` 身份写进 s2，B 就能读到。
- 改法：
  - 签名改成 `fileAccess?(vm: string, botId: string, threadId: string)`，与 `liveAccess` 带身份的做法一致。接线约定写明：只有该机器人当前仍占用这块屏时才返回访问器，否则返回 `undefined`。
  - `handOverWithAccess` 和 `mintFileWithAccess` 传入卡片记录的 botId 和 threadId。`secret.vm` 以 `shared:s` 开头却拿不到访问器时直接报错（走 `userError`，文案中英葡三份都要有），不写文件。
  - `sweep` 只删文件，保持现有调用；如需新签名，传卡片自己的 botId 和 threadId。
  - report.md 接线说明里对应的那条改成新签名和归属校验要求。
- 补测试：屏改分给别的机器人后，旧卡片保存返回错误，且屏里不产生文件；原机器人仍占用这块屏时照常写入。
