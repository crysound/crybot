## 必改
1. **大体积浏览器资料批量写入必然失败**
   - 位置：`server/screen-profile-files.ts:60-82`（transferProfile 把所有文件读进内存）、`server/screen-files.ts:158-163`（writeMany 整批 base64 + JSON.stringify）、`server/screen-files.ts:78`（所有动作统一 30 秒超时）。
   - 问题：Node 单个字符串上限约 536870888 字符，折合原始数据约 383MiB，超过必抛；峰值内存是原始数据、base64、JSON 三份叠加；30 秒对几百 MB 太短（单屏路径 `local-vm-profiles.ts:58,101` 是 5 分钟）；Chrome 的 Cache、Code Cache、Service Worker 等缓存都被带上。
   - 后果：屏抢救永远失败、rescue-pending 一直留着、重建卡死；`migrateLegacyBrowserProfilesToScreen` 同路径，资料大时 s1 拿不到初始资料，违反「单屏 → 多屏迁移后浏览器登录仍在」。
   - 改法（推荐前两条一起）：
     - 浏览器资料跳过缓存目录（至少 `Cache`、`Code Cache`、`GPUCache`、`Service Worker/CacheStorage`、`ShaderCache`、`GrShaderCache`、`DawnCache`、`component_crx_cache`），保留 Cookies、Login Data、Local Storage、IndexedDB 等登录相关内容。
     - 改成流式传输：宿主侧把暂存目录打成 tar 流经 stdin 交给 `exec -u crybot-sN tar -x --no-same-owner`（或按字节分批，每批 ≤64MiB，exec 次数随字节数增长、与文件数无关）。解包前后照样检查越界和软链接。不得一次性把整棵树读进内存。
     - 屏抢救/迁移的超时与单屏路径对齐（5 分钟）。
     - 代码和 report 里声明的上限改成真实可达的值。
   - 补测试：超过 383MiB 的资料能完成（用稀疏文件或 mock 掉底层写入，不必真造大文件）；缓存目录被跳过、登录相关文件保留。
