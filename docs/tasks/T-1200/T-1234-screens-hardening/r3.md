## Actions 实测结果（第 2 轮提交 0584c662）
「Real VM screens」失败在：

```
Error: crybot-s1 cannot query s2 display: unexpectedly succeeded
    at expectCommandFailure (scripts/smoke-screens-container.mjs:253:9)
    at async scripts/smoke-screens-container.mjs:315:3
```

即以 crybot-s1 身份执行 `DISPLAY=:2 xset q` 成功：屏 s1 的进程能连上屏 s2 的 X 服务器（可截屏、注入键鼠），跨屏隔离不成立。原因：`server/container-screens.ts:30` 的 Xvnc 启动参数没有 `-auth`，全仓也没有 xauth/xhost 配置；X 服务器不带授权时放行本机连接，Linux 上客户端先连抽象套接字 `@/tmp/.X11-unix/XN`，抽象套接字不做文件权限检查。

## 必改 1（安全，产品代码）：每块屏的 X 服务器只接受本屏用户
- 给每块屏生成独立的 MIT-MAGIC-COOKIE（每次容器启动随机生成，不落进镜像、不进日志），写到只有该屏用户可读的授权文件（例如 `/run/crybot/screens/sN/` 下，属主 crybot-sN、0600 或同目录现有 passwd 的约定），Xvnc 用 `-auth <该文件>` 启动。
- 本屏需要连 X 的程序（session/startxfce4、cua-driver、`screen-wait-display`、屏内 exec 即 `screenIdentityArgs`、服务端经 root 对该屏做的截屏/探测等）都要拿到 `XAUTHORITY` 指向本屏授权文件。注意第 1 轮的约束仍然有效：supervisor 的 program 段里**不能**出现 `environment=`，环境变量要在降权之后由包装程序设置（同现有 screen-program/screen-process 的做法）；单测里「program 段无 environment=」的断言保留。
- 全仓 grep `DISPLAY`、`xset`、`scrot`、`x11grab`、`screenDisplay`，把多屏路径上所有 X 客户端都核对一遍，单屏（非多屏容器、DISPLAY=:1 的原有 cua 桌面）行为不变。
- 如果你判断还需要 `-nolisten tcp` 之类加固，可以加，但核心是授权，不要靠改套接字权限凑。
- 单测：断言 Xvnc 命令含 `-auth` 且路径按屏区分；授权文件生成脚本的属主/权限；屏内 exec 参数带本屏 XAUTHORITY。
- 冒烟（`scripts/smoke-screens-container.mjs`）现有的「crybot-s1 不能查询 s2 显示」检查**不得放宽**；正向对照（crybot-s2 `DISPLAY=:2 xset q` 成功）保留且要在新授权下仍成功。再加一条：crybot-s1 读不到 s2 的授权文件。

## 必改 2：sudo 拒绝原因漏了 no-new-privileges
- `scripts/smoke-screens-container.mjs` 约 317 行 `sudoDenied` 只认 sudoers 文本。冒烟用 docker + linux 起容器，按 `server/container-computer.ts:775`、`server/container-isolation.ts:49-51` 一定带 `--security-opt no-new-privileges`，sudo 实际报 `The "no new privileges" flag is set, which prevents sudo from running as root.` 或 `effective uid is not 0`，退出码 1。正则补上 `no new privileges|effective uid is not 0`，其他失败原因仍要报错。
- 另外以 root 断言 `/etc/sudoers.d/cua` 不存在，证明 sudoers 已清理。
