# T-1228-wiring 第 10 轮：查清「首次工具调用才绑定屏」用例的失败根因并修复

## 现象
server/local-vm-screens.e2e.test.ts 的用例「Auto binds its MCP to the assigned screen only on its first tool call」：
- GitHub Actions 上最近 3 次 CI（3 个不同提交）都失败，位置都是 :109 `expect(result).not.toHaveProperty("isError", true)`，由 :270 调用。CI 机器是 2 核、整套测试并行，负载高。
- 主机上整文件跑 5 次失败 1 次；单独跑这一个用例 3 次都通过。
- 失败时返回的是工具结果里带 isError 的对象，测试没有把 content 打出来，所以看不到具体错误文字。

这是多屏的核心行为（懒加载 MCP 在第一次工具调用时才拿到服务端分配的屏号并绑定），不能当偶发处理，也不能只加超时或加重试了事。

## 要做
1. 先改断言，让失败时把 result.content 的文字带进失败信息（方便以后排查）。
2. 读懂这条路径：server/lazy-container-mcp.ts 怎么在第一次工具调用时向服务端要屏号、内部门禁返回什么、屏还没就绪/还在启动时返回什么、超时多少；对照测试里的 fixture（假容器运行时、屏就绪时机）。
3. 在负载下复现：例如同时跑别的测试文件制造 CPU 压力，或在 fixture 里把屏就绪人为推迟几百毫秒～几秒，看是否稳定复现成 isError。
4. 找到根因后修根因：
   - 如果是产品代码在屏还没就绪时直接报错（而真实用户在慢机器上也会撞到），就改产品代码：在合理时限内等屏就绪，或返回可重试的明确状态并由 MCP 端等待重试；
   - 如果确实只是测试 fixture 的时序假设不对（例如没等屏就绪就调工具，而产品行为是正确的），就改测试的等待条件，等到明确的就绪信号，不用固定 sleep。
   - 报告里写清证据：复现方法、根因所在代码行、为什么这样改是根因修复。
5. 补一条能稳定复现原问题的测试（例如推迟屏就绪），修复前失败、修复后通过。
