## 必改 1（安全审查中危 M1）：飞书配置为空时，旧的飞书设备会话不会被吊销
- 现状：`server/index.ts` 约 716-722 行只在 `FEISHU_CONFIG` 非空时才调用 `revalidateFeishuSessions`。清空 `CRYBOT_FEISHU_TENANTS`、去掉 `CRYBOT_FEISHU_APP_ID`、Secret 为空或读不出、设了 `HOSTED_WORKSPACE`/`CLOUD_TEAM` 时，`feishuLoginConfig` 都返回 null，重启后已签发的飞书设备会话（最长 90 天、可能带 admin）仍然有效。
- 改法：
  - 启动时不论配置是否为空都执行核对。
  - 配置为 null 时，吊销全部 `source=device` 且 `accessIdentity` 以 `feishu:` 开头的会话；其他会话（Access 会话、非飞书设备会话）不受影响。
  - 启动日志写一行固定文案说明吊销了多少条（只写数量，不写身份）。
- 测试（`server/sessions.test.ts` 或现有核对测试所在文件）：配置为 null 时飞书设备会话被吊销、Access 会话和非飞书会话保留；配置正常时原有核对行为不变。

## 必改 2（复审建议，一并修）：客户端断开后服务端仍签发设备会话
- 现状：`server/feishu-routes.ts` 约 39-51 行，客户端在交换途中断开，服务端照样调飞书 token 接口并签发会话。这些令牌永远到不了客户端，却占着同一身份 10 个设备名额，会按 `lastSeenAt` 挤掉最早的真实设备，网络差反复重试时可能把用户另一台设备踢下线。
- 改法：拿到飞书结果后、签发前检查连接是否已断（如 `req.socket.destroyed` / `res.writableEnded` / `req.aborted` 等，以实际可用的为准）；已断就不签发。写响应失败时吊销刚签发的那条。
- 测试：等假飞书收到 token 请求后再断开客户端（不要用固定 10ms），断言该身份没有新增设备会话；断开后正常交换仍 200。
