## 必改
1. `server/sessions.test.ts`「两类会话分开计数」（约 834-856 行）：现在 Access 用 `"owner"`、设备用 `"feishu:union_example"`，两个身份本来就互不影响，测试没有意义。改成**同一个身份** `feishu:union_example`：先签发设备会话，再签发 5 次 Access（照现在写法中间关闭、重开 registry），断言设备会话仍有效；再签发 11 次设备会话，断言最后一个 Access 会话仍有效。同时断言每次签发的令牌都不同，被吊销的是 `lastSeenAt` 最早的那个。验证方法：临时把 `issueAccess` 的过滤条件改回只按 `accessIdentity`，这条测试必须变红（报告贴出红灯输出，再改回）。
2. `maxAgeAt` 补测 `renew` 分支：`maxAgeDays: 20`，时钟推进 10 天，调 `registry.renew(id)`，断言 `expiresAt === maxAgeAt`；再推过 maxAgeAt，断言 `authenticate` 返回 null。验证：临时删掉 `sessions.ts` 里 `record.maxAgeAt ?? Infinity` 这一处，测试必须变红。
3. `server/feishu-routes.test.ts` 测试服务器的兜底：现在路由不处理时也回 `404 {error:"not_found"}`，和路由自己的 404 分不出来。兜底改成 `418 {error:"fallthrough"}`，让「所有路径和方法都 404」的每条断言都能分辨路由是否真的处理了。
4. 补两组测试（先红后绿，报告贴改前失败输出）：
   - `persist()` 失败：照 `revalidateEmailSessions` 现有测试的写法 spy `atomic.writeFileAtomic` 让它抛错，断言 `console.error` 被调用一次、内存里的会话已吊销、调用不抛异常。
   - 假飞书端到端：路由测试里真的用 `server/testing/fake-feishu.ts`，走 authorize 302（断言 Location 带回 state）、S256 challenge 比对（用 code_verifier 算 SHA-256 base64url 与 challenge 比，错的 verifier 被拒）、按端点注入延迟触发真正的超时（不是 20ms 后抛错的假 fetch）、客户端中途断开。
5. `server/index.ts:709` 那行末尾追加的 `; const HOSTED_WORKSPACE = hostedWorkspaceConfigured();` 单独起一行。不要把多条语句挤到一行。
