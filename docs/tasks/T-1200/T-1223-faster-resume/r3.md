## 必改
1. **`server/computer-call-gate.ts:38`：readinessOnly 等待时不发「正在唤醒电脑…」。**
   懒加载轮里模型只看得到 search_tools、describe_tool、call_tool，第一次用电脑几乎都先调 search_tools，它走 gate 时带 `readinessOnly`（`server/lazy-container-mcp.ts:67`、`:97`），在 `settledWithin` 里等完整唤醒（真实约 6.5 秒）却不发提示；等 call_tool 来时唤醒已完成，也不会再发。结果常见路径上用户等了几秒却看不到提示。这是第 2 轮引入的倒退。
   改法：readinessOnly 只跳过「有人占用屏幕」检查、claimResource、ACT_WITHIN 和 journal；`onWaiting` 照常触发，每个 slot 仍只触发一次。补测试：先 search_tools 等唤醒 → 提示恰好出现一次；之后 call_tool 不再重复提示。lazy MCP 层或 fixture 层都可以，fixture 更好。

## 一起做的建议
2. **60 秒冷却范围（`server/local-vm-resume.ts:30-32`）**：现在记录所有非取消的 claim 失败，包括「正在启动、停止或替换」（`server/index.ts:8014` 一带，镜像更新、模式切换期间）和租约绑定失败这类暂时性原因，而且生命周期事件不会清冷却。改成只记录启动或桌面就绪本身的失败；并在 `invalidateContainerComputerStatus` 这类生命周期事件（手动启动、停止、镜像更新、模式切换）时清掉对应目标的冷却。补测试：暂时性失败不进冷却；进了冷却后发生生命周期事件，下一轮会重新尝试。
3. **合并请求沿用第一个调用方的 isCurrent（`server/local-vm-ready.ts:22`）**：后加入的调用方拿到 prior 的结果、发现未就绪而自己的轮次仍在进行时，用自己的 `isCurrent` 再走一次，不要直接报 not ready、也不要因此进冷却。补一个两个调用方、第一个先结束的单测。
4. **`server/auto-vm-claims.ts:71`**：Local VM 后台唤醒对暂时性网络错误不再重试。恢复原来的重试行为（和改前一致）；若你确认不重试是必要的，在 report 里写清原因，不要两头都不说。
