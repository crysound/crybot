## 本轮必须做的

### 1. 安全审查「中」：恶意同机 App 可以自带 pk 主动发起接力
攻击方式：恶意 App 注册 `crybot://`，自己生成密钥对，用系统浏览器打开 `/auth/app-handoff?state=..&pk=<自己的公钥>`。浏览器里已有有效的 Access 登录，页面就会自动跳回，恶意 App 解出 JWT。

要彻底解决，需要改用 App Links / Universal Links，那属于后续任务。本轮先做缓解：

- **接力页不再自动跳转。**
  - 删掉 `<meta http-equiv="refresh">`。
  - 页面必须让用户亲手点按钮才跳回 App。按钮仍然是指向回跳地址的普通链接。
- **页面写明是在给谁、登录什么。**
  - 标题写「在 Cry Bot App 中登录」。
  - 显示当前账号，取 JWT 里的 email，要转义。
  - 加醒目提示，中文：「只有你刚刚在 Cry Bot App 里点了登录，才点下面的按钮。如果你没有这样做，请直接关闭此页。」英文对应翻译。
  - 中英文按 `Accept-Language` 选择，沿用现有的写法。
- 其余保持不变：不用内联脚本，CSP 不变，三个响应头不变。HTML 里仍然不能出现明文 JWT。
- **`docs/self-hosting.md` 接力说明里如实写清残余风险。** 写明这个协议防住了被动截获回跳，但防不住同机恶意 App 主动发起接力，只能靠用户确认这一步来缓解。彻底的办法是 App Links / Universal Links。不要写成能防住恶意 App。
- **测试：**
  - 成功时 HTML 里没有 `http-equiv="refresh"`。
  - 有指向回跳地址的按钮。
  - 显示的 email 已转义。比如用 `<b>` 这类字符做 email，断言输出是转义后的结果。
  - 中英文提示文案都要断言。

### 2. 安全审查「低」/ 审核建议：state 对不上的回调直接忽略
两端收到 `crybot://auth`、但 state 和挂起的对不上时，**直接忽略**：不清挂起的 state 和私钥，不显示错误面板，也不打断正在进行的登录。

涉及位置：
- iOS：`ViewController.swift` 约 200-202 行（`failLogin()` 那里）。
- 安卓：`MainActivity.kt` 约 409-412 行（`clearPendingLogin()` 加 `showError` 那里）。

state 对上了但解密失败，仍然按登录失败处理。
