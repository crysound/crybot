## 上一轮情况
第 5、6 轮把标签枚举的 encode 改为直接编码载荷，并新增 `Packages/CryKit/Tests/CryCoreTests/WireMessageStackTests.swift`。Linux 上 CryKit 全部测试通过，但 Actions「Mobile builds」的 macOS 包测试崩溃：

```
Test Case '-[CryCoreTests.WireMessageStackTests testDetachedRoundTripOfLargeMessageCollections]' started.
error: Process '.../xctest .../CryKitPackageTests.xctest' exited with unexpected signal code 10
```

即新回归测试在 macOS 上真的复现了栈溢出（SIGBUS）。原因判断：`Task.detached` 跑在协作线程池上，macOS/iOS 这些线程栈只有 512 KiB；Linux 线程栈默认 8 MiB，所以 Linux 上测不出来。Debug 构建下 `WireMessage` / `WireMessageFields` / `ThreadPage` / `BotsSnapshot` 的 Codable 代码（合成的或手写的 `init(from:)` / `encode(to:)`）单帧占栈很大，嵌套几层就超过 512 KiB。真机上 App 的解码同样在协作线程上跑，这是要修的产品缺陷，不是测试问题。

## 必改
1. **让回归测试在 Linux 上也能复现**：`WireMessageStackTests` 改为（或新增一个用例）在显式 `Thread` 上执行同样的编码再解码，`stackSize = 512 * 1024`（与 Apple 平台协作线程一致），用信号量或 `XCTestExpectation` 等待结果；保留现有 `Task.detached` 用例。这样 Linux 上修复前应当崩溃、修复后通过，协调者会在 Linux 先跑一次确认。
2. **降低解码/编码路径的栈占用，直到 512 KiB 线程上 500 条消息的数组、ThreadPage、BotsSnapshot 编解码都通过**。先找出到底是哪些类型的单帧大（读 `WireModels.swift`、`JSONValue.swift` 及 `WireMessage`、`WireMessageFields`、`WireBot`、`BotsSnapshot` 相关模型），再按需选做法，常见做法：
   - 把大载荷改为堆上存储：`indirect` 枚举分支，或把字段很多的结构体（如 `WireMessageFields`）改为内部 `final class` 存储 + 写时复制的包装，对外 API、`Equatable`、`Hashable`、`Sendable` 和 JSON 线格式不变；
   - 手写的大 `init(from:)` 拆成若干小的 `@inline(never)` 辅助函数，避免一个帧里同时放下所有临时值；
   - 不要靠把工作挪到主线程或开大栈线程来绕过——App 里解码就发生在协作线程上。
3. 现有测试（CryKit 全部包测试、`CryBotTests`）断言不改；JSON 编解码结果与修改前逐字节一致（已有的 round-trip / fixture 测试要继续通过）。
