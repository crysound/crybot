## 必改
1. **编译不过**（`mobile/ios/CryBot/App/Logic/FrameCursor.swift:9-10`）：`JSONValue.number` 关联的是 `Decimal`（`Packages/CryKit/Sources/CryCore/JSONValue.swift:7`），`Decimal` 没有 `rounded()`，也不能 `Int64(seq)`。改为先转字符串再解析整数，例如 `case .number(let raw)` 后 `Int64("\(raw)")`，并要求 0 ≤ n ≤ 9_007_199_254_740_991，否则视为无游标。复审按此改后 Types、LaunchOptions、App/Logic、Store 的 Swift 6 类型检查全部通过。
2. **hello 游标采用过早，会永久跳过快照或重放帧**（`mobile/ios/CryBot/Store/AppStore.swift:303,308-313`）：
   - 现在 hello 的 cursor 在快照成功前就写进 `cursor`；快照失败只在 `id == connectionID` 时才清，而 pauseRealtime 会先换 connectionID。复审探针：首次连接 resumed=false、快照未完成时进后台，回前台续传 since 是 hello 的 `S:5`，服务端判 resumed=true，此后再也不拉快照，首次启动状态一直为空。
   - resumed=true 时 hello.cursor 是服务端当前 lastSeq（`server/index.ts:14729`），若在处理完 hello、还没处理第一个重放帧时断线，下次续传会跳过这些重放帧。
   - 改为：resumed=false 时，只有快照成功后才采用 hello.cursor；resumed=true 时保留原游标（只随后续帧的 seq 前进）；快照失败或被取消时，不论 connectionID 是否变化，都把游标置为「需要快照」。
   - 补测试：(a) 快照挂起时 pause → resume，第二次 since 不能是 hello 的游标，或者重连后必定再拉快照；(b) resumed=true 后、重放帧到达前断线，下次 since 仍是旧游标。
3. **每帧都等一次未读数请求**（`AppStore.swift:314-320`）：流式输出时每个 message.patch 都 `await refreshInboxCount()`，请求风暴且后续帧排队（复审：计数接口延迟 300ms 时 10 个 patch 用了 2.71s），接口慢时还会被 40 秒无帧判断误判为断线。改为不在帧循环里 await：合并刷新（同一时间最多一个在途请求，结束后若期间有变化再补一次），message.patch 这类高频帧不触发。`ConnectionTests.swift:162` 断言 `inboxRequestCount == 5` 一起改。补测试：计数请求挂起时后续帧照常处理、多帧只产生有限次请求。
4. **report.md 第 1 轮内容被删**（`docs/tasks/T-1200/T-1221-app-shell/report.md:3-5`）：从提交 9d5d38f1 恢复第 1 轮的「文件改动」「覆盖表对应项」「需要协调者处理」几节（ConversationRef、RespondAction、DesktopTarget 字段选择，loadOlder 与 LiveState 历史 API 建议，PersonRef(member:) 类型缺口，LoginRouter 与 WebHost 衔接），只删与 brief 重复的说法。各轮追加，保留前几轮。
